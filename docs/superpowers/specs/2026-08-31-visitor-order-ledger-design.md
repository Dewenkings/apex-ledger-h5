# Apex Ledger 访客订单账本设计

## 背景与问题

Apex Ledger 使用一组仅保存在 Vercel 服务端的 OKX Demo Trading 凭证，为公开作品集访客提供真实 OKX 模拟盘下单体验。生产证据显示，下单接口返回 `201`，但随后 OKX 的 `orders-pending` 与 `orders-history` 均返回空数组。空结果发生在应用的会话归属过滤之前，因此不能继续把 OKX 账户级列表接口当作作品集订单列表的唯一数据源。

当前身份同时承担了访问门禁和订单归属两个职责。门禁会话有效期为 4 小时，因此即使订单归属记录仍在 Redis 中，同一访客在新会话中也无法自然恢复历史订单。公开作品集还共享同一个 OKX Demo 账户，不适合向所有访客公开账户级订单或允许互相撤单。

## 目标

- OKX 接受订单后，即使账户级列表接口暂时为空，访客也能在订单页看到订单。
- 同一浏览器在 30 天内重新访问时，能够恢复自己的模拟订单。
- 不同访客互相看不到、也不能撤销对方的订单。
- OKX 仍是订单状态的权威来源；Redis 是访客索引、展示快照和故障回退来源。
- OKX Demo API Key、Secret 和 Passphrase 始终只存在于服务端。
- 保持现有单笔金额、速率和未完成订单数量限制，并为公开演示增加全站保护能力。

## 非目标

- 不接入 OKX 实盘交易、充值或提现。
- 不实现注册账号、跨设备登录或永久订单档案。
- 不向访客展示完整共享 OKX Demo 账户的全部订单。
- 不把 Redis 快照伪装成实时 OKX 状态。
- 本阶段不实现 WebSocket 私有订单推送；订单状态通过 REST 同步。

## 方案选择

采用“访客隔离的双数据源订单账本”：

1. OKX Demo 负责实际模拟下单和权威订单状态。
2. Redis 保存访客身份、订单索引和最后已知订单快照。
3. 订单列表先从 Redis 找到当前访客的订单，再按 `instId + ordId` 调用 OKX 单笔订单接口刷新。
4. OKX 暂时不可用时返回 Redis 快照，并明确标记同步状态和最后同步时间。

不采用全账户共享列表，因为它会暴露其他访客的活动并允许越权撤单。不继续采用纯门禁会话过滤，因为 4 小时会话不适合订单历史恢复。

## 身份模型

系统拆分两种签名 Cookie：

### 访问门禁会话

- Cookie：沿用 `apx_demo_session`。
- 有效期：4 小时。
- 职责：证明访客已输入正确的 Demo Access Code，允许调用交易私有接口。
- 过期影响：访客需要重新输入访问码，但订单归属不会丢失。

### 匿名访客身份

- Cookie：新增 `apx_visitor`。
- 内容：随机 UUID、版本和过期时间，使用 `SESSION_SECRET` 做 HMAC 签名。
- 有效期：30 天，`HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/`。
- 职责：稳定标识同一浏览器中的访客工作区。
- 创建时机：首次成功建立门禁会话时创建；已有合法 Cookie 时复用。
- 过期影响：创建新工作区。旧数据继续按 Redis TTL 自动清理，但无法从新身份访问。

门禁会话保存 `visitorId`，所有订单接口同时验证有效门禁会话和一致的访客身份。服务端绝不接受客户端在请求体中自报 `visitorId`。

## Redis 数据模型

### 订单快照

Key：`apx:order:{ordId}`

字段：

- `visitorId`
- `ordId`
- `clOrdId`
- `instrument`
- `side`
- `orderType`
- `price`
- `size`
- `filledSize`
- `averagePrice`
- `status`
- `createdAt`
- `updatedAt`
- `lastSyncedAt`
- `syncState`: `synced | pending | stale`

TTL：30 天。每次成功同步可续期至 30 天，但总保留时间不要求超过作品集演示需要。

### 访客订单索引

Key：`apx:visitor-orders:{visitorId}`

类型：Sorted Set，member 为 `ordId`，score 为创建时间戳。TTL：30 天。列表默认读取最近 50 条，避免无界查询。

### 幂等、限速与开放订单集合

沿用现有 key，并把归属维度从短期 `sessionId` 调整为稳定 `visitorId`。订单快照成为撤单授权和开放订单统计的统一来源。旧 `apx:owner:{ordId}` 记录不做批量迁移；新代码在兼容期内可读取，但新订单只写新结构。

## 下单流程

1. 验证门禁会话和访客 Cookie 一致。
2. 校验交易对、方向、类型、数量、价格和参考价格。
3. 基于 `visitorId` 和 IP 执行限速、名义金额及开放订单限制。
4. 基于 `visitorId + Idempotency-Key` 获取幂等声明。
5. 生成 `clOrdId`，调用 OKX Demo `POST /api/v5/trade/order`。
6. OKX 返回接受回执后，在返回 `201` 之前原子性地保存订单快照和访客索引。
7. 初始快照状态为 `pending`，随后调用 OKX `GET /api/v5/trade/order?instId=...&ordId=...` 做一次最佳努力同步。
8. 如果 OKX 回执成功但 Redis 写入失败，服务端返回不可用错误并记录安全诊断；幂等键允许后续通过 `clOrdId` 对账，避免盲目重复下单。

初始快照保证“已接受订单立即可见”，单笔查询保证后续状态来自 OKX，而不是依赖账户级列表接口。

## 查询订单流程

1. 验证门禁会话和访客身份。
2. 从访客 Sorted Set 读取最近 50 个 `ordId`。
3. 批量读取对应 Redis 快照，丢弃缺失或归属不匹配记录，并清理脏索引。
4. 对最近订单做有界并发同步：每个订单使用已保存的 `instrument + ordId` 调用 OKX 单笔订单接口。
5. 成功时更新 Redis 快照并返回 `syncState=synced`。
6. 超时、限频或 OKX 暂时失败时返回最后快照，设置 `syncState=stale`，保留 `lastSyncedAt`。
7. 单条同步失败不能让整个订单列表失败。

账户级 `orders-pending` 和 `orders-history` 不再参与访客列表主路径，可保留为管理员诊断能力，但不向公开前端暴露。

## 成交记录

成交记录只能关联当前访客已知订单：

- 对 `filled` 或 `partially_filled` 的订单，使用 `ordId` 调用 OKX 成交查询接口；若接口不支持精确单笔过滤，则获取有限结果后仅保留当前访客订单集合中的记录。
- Redis 可保存最近一次成交快照作为回退。
- 任何成交记录都必须通过 `ordId` 和订单快照归属双重校验。

本阶段优先保证订单状态和订单历史可靠；成交明细保持现有 UI，但不得展示其他访客的共享账户成交。

## 撤单流程

1. 根据 `ordId` 读取 Redis 订单快照。
2. 验证快照 `visitorId` 与当前签名访客身份一致。
3. 使用快照的 `instrument` 调 OKX 单笔订单接口确认订单仍可撤销。
4. 调用 OKX Demo 撤单接口。
5. 更新快照状态和同步时间。

客户端传入的交易对不再作为授权依据，仅作为可选一致性校验，从而避免修改请求体越权撤单。

## 前端行为

- 订单列表中的订单始终来自当前访客工作区。
- `synced`：显示正常的 PAPER LIVE 状态。
- `pending`：显示“已提交，正在同步 OKX”。
- `stale`：显示“上次同步于 …”，提供手动刷新按钮。
- 无个人订单时显示“尚无个人模拟订单”和下单入口。
- 可增加独立的“示例流程”卡片，但必须明确标记为示例数据，不能混入真实 OKX Demo 订单列表。
- 余额继续明确标注为“共享 OKX Demo 虚拟余额”，避免访客误认为是自己的独立账户资产。

## 公共演示保护

- 保留单笔名义金额不超过 250 USDT。
- 保留每个访客最多 5 个未完成订单。
- 保留访客与 IP 分层限速。
- 增加 Redis 全站日订单数量和日名义金额阈值；达到阈值时只禁用新下单，不影响行情、历史和示例浏览。
- 不开放提现、充值或实盘切换配置。
- 日志只记录错误类别和数量，不记录密钥、Cookie、完整订单号或访问码。

## 错误处理

- OKX 下单明确拒绝：不写成功快照，向前端返回安全的业务错误。
- OKX 下单超时：使用 `clOrdId` 查询单笔订单对账；结果未知时返回“结果待确认”，禁止使用新幂等键盲目重试。
- Redis 写入失败：不把订单当作可展示成功，记录诊断并返回服务不可用。
- OKX 状态同步失败：返回已有快照并标记 `stale`。
- 快照损坏或归属不匹配：不返回该订单，清理索引并记录计数诊断。
- 访客 Cookie 丢失或过期：建立新工作区，不尝试公开共享账户订单。

## 测试策略

所有行为变更遵循测试先行：

- 身份测试：访客 Cookie 创建、复用、过期、签名篡改、门禁会话绑定。
- 存储测试：订单快照写入、索引、TTL、归属隔离、脏索引清理。
- 服务测试：OKX 列表为空时订单仍从账本可见；单笔同步成功；同步失败回退；不同访客隔离。
- 撤单测试：仅快照所属访客可以撤单，客户端伪造交易对不能越权。
- API 测试：下单成功在响应前写入账本；门禁过期但重新登录后同一访客恢复订单。
- 前端测试：`pending`、`synced`、`stale` 和空状态展示。
- 回归验证：完整 Vitest、ESLint、TypeScript、Next.js production build。

## 上线与回滚

1. 先上线兼容读取：新订单写新账本，旧归属记录仍可用于当前会话内查询。
2. 生产验证一个限价订单：确认立即可见、刷新仍可见、单笔状态能同步。
3. 验证重新建立门禁会话后同一浏览器仍可见。
4. 验证第二个隐身窗口看不到第一个访客订单。
5. 稳定后移除账户级列表主路径和临时计数诊断。

回滚时可以恢复旧查询服务；新 Redis key 使用独立命名空间，不影响旧数据。OKX Demo 中已创建的订单不因应用回滚而删除。

## 成功标准

- 下单返回成功后，订单页在一次刷新内可见订单。
- OKX 账户级列表继续返回空时，订单仍可见且能通过单笔接口更新。
- 同一浏览器 30 天内重新输入访问码后可恢复订单。
- 不同访客无法查询或撤销对方订单。
- OKX 暂时不可用时页面展示最后快照和过期提示，而不是空数组。
- 生产日志和客户端响应不暴露任何凭证或敏感会话数据。
